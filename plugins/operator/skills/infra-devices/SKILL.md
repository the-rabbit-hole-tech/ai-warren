# Network devices

- Find out why a port is in its state before you change it. On any network device, before changing any port (err-disabled, shut, a trunk or anything else), check the err-disable cause and the logs, its LLDP or CDP neighbours, PoE draw and MAC table. A port re-enabled without that once looped the network and took another port offline.
- Learn each device's real commands, and keep them in the project. Before building any automation or rotation against a device, run its commands read-only on that exact device first. Where the CLI's `?` help is weak or missing, look up the device's model and running software version, and the vendor's command reference for that version. Record what works in a command index in the project's repo, per model and version, and make it that project's standing rule (its CLAUDE.md or AGENTS.md), not a global one. A command that works on the device but isn't in the vendor docs is indexed as learned on the device and marked "not in vendor docs" until a search confirms it.
- Read-only diagnostics, then a root-cause fix. Diagnose with read-only commands first (show, display, get). Fix the cause in a reviewed change, never with a workaround that leaves the device in an odd state.
- Test SSH keys one at a time. Test a key login with `-i <key> -o IdentitiesOnly=yes` for each key before calling access blocked. Without it, SSH offered the wrong key, got "rejected", and a day went into an approval detour.
- Type device commands literally in tmux. Send them with `tmux send-keys -l '<command>'`, then a separate Enter. Without `-l`, words that match key names ("end", "home") are sent as keys, so a switch never left config mode.
- Never send keystrokes into a pane with a live device session. A pane holding an SSH, console or serial session to a device gets no keystrokes it didn't ask for: no `/compact`, `/clear` or other slash commands, no broadcast or scripted `send-keys` loops, no `synchronize-panes`, no pasted buffers, and no `tmux send-keys` aimed by window name. Pick target panes by their running command (only `claude`), and name device panes so they stand out. A broadcast once typed "/compact" into a device's config mode.
- Infrastructure work: one session by default, never two on one device. Device work runs in one INFRA session by default. When a job is too big, split it into more infrastructure sessions under the usual rules, but only one session may hold a given device at a time: it claims the device first, and no two sessions run changes on the same device at once, because conflicting changes on one box are how outages happen.
- No real identifiers in anything public. Device configs, scripts, examples and tests in public repos use documentation addresses (`192.0.2.0/24`, `2001:db8::/32`) and invented names. A local forbidden-terms list is checked on every push.
- Check a hand-off against the device. Before applying config from a hand-off or document, check every named item (VRF, VLAN, interface, policy, object) against the live device; querying it live is fine. If they differ (the hand-off says INTERNET, the device has VRF_INTERNET_WAN), treat the hand-off as wrong, point out the difference and ask the operator. Never assume.
- Production needs an explicit go. The operator says whether a device is production or non-production, and each project stores that as a standing rule. Non-production devices can be changed freely. A production device, including a mixed or mid-setup one, needs an explicit go for each change.
- Show the diff first. Every change on a live device first shows its diff as a plain-text before-and-after in a code block: the current config lines marked -, then the proposed lines marked +. Prod or not.
- Credentials and secrets: see secrets:credential-rules.
